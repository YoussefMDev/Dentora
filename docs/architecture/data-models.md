# Initial Mongoose models

These schemas are groundwork for the already approved staff invitation and account-recovery requirements. They do not add API routes or workflows. Mongoose `autoIndex` is disabled on the connection and on each schema, so installing the application does not create collections or indexes in Atlas.

## Implemented schema inventory

| Model / collection                                 | Purpose                                                                 | Fields and rules                                                                                                                                                                                                                                                                                                                        | Indexes declared (not applied)                                                                                                                                                                               |
| -------------------------------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `StaffAccount` / `staffaccounts`                   | Represents an invited clinic staff account.                             | `email` (required string, trimmed and lowercased, maximum 254 characters, basic email shape); `passwordHash` (required string beginning with the Argon2id prefix); `role` (required `Admin` or `Staff`); `emailVerifiedAt` (required date); timestamps `createdAt` and `updatedAt`.                                                     | Unique `email` for case-normalized account uniqueness.                                                                                                                                                       |
| `StaffInvitation` / `staffinvitations`             | Represents an invitation sent by an existing staff account.             | `email` (required, normalized string, max 254); `role` (required `Admin` or `Staff`); `tokenHash` (required 64-character lowercase hex digest, never the raw invitation token); `expiresAt` (required date); `acceptedAt` (nullable date, defaults to `null`); `invitedBy` (required ObjectId reference to `StaffAccount`); timestamps. | Unique `tokenHash`; TTL index on `expiresAt` for eventual cleanup. Application code must still compare expiry and consume invitations atomically; TTL cleanup is delayed and is not the authorization check. |
| `PasswordRecoveryToken` / `passwordrecoverytokens` | Represents a single-use recovery token associated with a staff account. | `staffAccount` (required ObjectId reference to `StaffAccount`); `tokenHash` (required 64-character lowercase hex digest); `expiresAt` (required date); `usedAt` (nullable date, defaults to `null`); timestamps.                                                                                                                        | Unique `tokenHash`; TTL index on `expiresAt` for eventual cleanup. Application code must still enforce expiry and single use while changing the password.                                                    |

Mongoose's collection names above follow its standard pluralization of the model names. No code currently writes documents, and no indexes have been created in a database. Unique constraints are only effective once the indexes are applied through a reviewed deployment/migration step.

## Deferred entities

| Entity                        | Current decision                                                                                                                                                                                                     |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Appointment / patient booking | The Angular booking flow is explicitly demo-only. The product has rules for a future real workflow, but real booking persistence and patient-data handling require a separate approval and design.                   |
| Contact message               | The current contact flow is demo-only. Persistence, retention, and access policy need approval before storing submissions.                                                                                           |
| Gallery item / image          | A staff-managed gallery is in the MVP, but upload validation, storage access, privacy, and patient-consent requirements are not finalized. Do not create records or publish patient imagery until those are settled. |
| Clinic schedule / timezone    | One configurable clinic timezone and hours are required for the future booking experience, but it is not yet decided whether this configuration belongs in MongoDB or deployment configuration.                      |
| Service content               | Current service content is local demo content. It can remain static until there is a concrete need for staff-managed content.                                                                                        |

## Security limits

- These model validators are a second validation layer for stored documents; future route handlers must continue validating incoming requests with Zod.
- Password hashing, email delivery, invitation/recovery token generation and hashing, atomic single-use consumption, MFA secrets, sessions, authorization, and audit logging are not implemented here.
- Admin MFA is required before production use with real patient data. The storage/encryption design for MFA factors is not included in this model foundation and must be resolved before authentication is production-ready.
- The schema-level index definitions are not automatically sent to Atlas. A later reviewed migration step must create indexes and handle duplicate data before writes rely on uniqueness.
